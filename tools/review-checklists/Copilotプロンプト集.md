# Copilot プロンプト集（設計レビューの調整用）

`Invoke-DesignReview.ps1` を実際の設計書に合わせて調整するときに、Microsoft 365 Copilot に貼り付けて使うプロンプトです。
`【 】` の部分を書き換えてから使ってください。

| # | 使う場面 | 作られるもの |
| --- | --- | --- |
| [1](#1-社内の観点から観点表を作る) | 社内のレビュー観点・チェックリストがある | 観点表の行 |
| [2](#2-実際の設計書から観点表を作る) | 観点の元になる資料がなく、設計書だけがある | 観点表の行 |
| [3](#3-判定基準を具体的にする) | 観点表の判定基準があいまい | 書き直した判定基準 |
| [4](#4-対象設計書のパターンを決める) | 対象設計書・参照設計書の書き方が分からない | ファイル名のパターン |
| [5](#5-ai-の指摘と人のレビューを比べる) | AI の判定が合っているか確かめたい | 観点表の修正案 |
| [6](#6-判定のぶれを確かめる) | 同じ依頼で毎回結果が変わる気がする | ぶれやすい観点の一覧 |
| [7](#7-回答形式を出し直させる) | 回答を取り込めないと警告が出た | 形式どおりの回答 |
| [8](#8-レビュー結果を要約する) | レビュー会議・報告に使いたい | 指摘の要約 |
| [9](#9-ツールの改修依頼を整理する) | ツール側の変更が必要そう | 改修依頼のメモ（社外秘を含まない） |
| [10](#10-差分から改訂履歴の下書きを作る) | 設計書を改版した | 改訂履歴の下書き |

## 使うときの共通の注意

- **プロンプトごとに新しいチャットを始めてください。** 前の会話の内容が混ざると結果がぶれます
- 設計書は、ファイルを添付するより **`-PromptOnly` で作った依頼文（`design-review\prompts\R001.txt` など）の中身を貼る**方が確実です。セル番地付きのテキストになっているので、Copilot が場所を正しく指せます
- Copilot が出した表は、表の上で右クリック →「コピー」して Excel に貼ると、そのままセルに分かれます
- 観点表の列: `観点ID / 分類 / 観点 / 判定基準 / 重要度 / 対象設計書 / 参照設計書 / 有効`（ほかに、ツールで確かめる観点の `確かめ方 / ツールの確認`。下のプロンプトでは作らないので、[ツールで確かめる観点](../README.md#ツールで確かめる観点確かめ方ツールの確認) を見て書き足してください）

---

## 1. 社内の観点から観点表を作る

社内のレビュー観点表・チェックリスト・開発標準のレビュー規約などを添付するか、内容を貼り付けて使います。

```
添付（または下に貼り付けた）レビュー観点をもとに、Excel の【詳細設計書】を AI にレビューさせるための観点表を作ってください。

【出力形式】
次の列の表で出力してください（Excel に貼り付けて使います）。前置きやまとめは不要です。
観点ID | 分類 | 観点 | 判定基準 | 重要度 | 対象設計書 | 参照設計書 | 有効

【条件】
- 観点ID は分類ごとの英字 1 文字＋2 桁の番号（例: S01、T01）。重複させない
- 判定基準は、AI が設計書の記載だけを見て OK／NG を判断できるよう具体的に書く
  - 「適切か」「妥当か」「十分か」のような主観的な言葉を使わない
  - 何がどこに書かれていれば OK なのかを書く（例:「入出力が I の項目すべてに桁数が記入されている」）
- 設計書だけでは判断できない観点（業務要件との整合、性能の妥当性など）は表に入れず、最後に「AI では判定できない観点」として箇条書きで挙げる
- 1 つの観点で確認することは 1 つにする（複数のことを確認する観点は分ける）
- 重要度は 高／中／低（高 = 見落とすと不具合や手戻りに直結する）
- 対象設計書は、観点を当てはめる設計書のファイル名のパターン（例: *画面設計書*）。すべての設計書なら *
- 参照設計書は、判定に別の設計書が必要な場合だけ書く（例: *メッセージ一覧*）。不要なら空欄
- 有効はすべて ○

【レビュー観点】
（ここに社内の観点を貼り付け）
```

## 2. 実際の設計書から観点表を作る

観点の元になる資料がない場合に、実際の設計書から観点を起こします。
`Invoke-DesignReview.ps1 【設計書のフォルダ】 -PromptOnly` で作った依頼文のうち、`【設計書】` 以降の部分を貼り付けてください。

```
下の設計書は、Excel の【画面設計書】をセル番地付きのテキストにしたものです（「行番号| 列:値」の形式）。
この種類の設計書をレビューするときに確認すべき観点を、設計書の構成（シート・列）に合わせて挙げ、観点表にしてください。

【出力形式】
次の列の表で出力してください。前置きやまとめは不要です。
観点ID | 分類 | 観点 | 判定基準 | 重要度 | 対象設計書 | 参照設計書 | 有効

【条件】
- この設計書に実際にあるシート名・列名を使って判定基準を書く
- 記入漏れ（必須の欄が空）、記載どうしの矛盾（同じ設計書の中で食い違う）、あいまいな表現、の 3 種類を中心にする
- 設計書の記載だけで判定できる観点に限る
- この設計書の中身について良し悪しは書かない（観点を作るだけ）
- 対象設計書は【*画面設計書*】、有効はすべて ○

【設計書】
（ここに依頼文の【設計書】以降を貼り付け）
```

## 3. 判定基準を具体的にする

観点表の行を貼り付けて、判定基準だけを書き直させます。判定がぶれる観点（[6](#6-判定のぶれを確かめる)）にも使えます。

```
下の観点表の「判定基準」を、AI が設計書の記載だけで OK／NG を判断できるよう具体的に書き直してください。

【条件】
- 「適切」「妥当」「十分」「必要に応じて」のような主観的・あいまいな言葉を使わない
- 何がどこに書かれていれば OK なのかを書く。シート名・列名が分かる場合は使う
- 観点の意図は変えない。1 つの判定基準で確認することは 1 つにする（複数ある場合は行を分けて、観点ID に -a、-b を付ける）
- 出力は元の表と同じ列の表で、変更した行だけ。最後の列に「変更理由」を追加する

【観点表】
（ここに観点表の行を貼り付け）
```

## 4. 対象設計書のパターンを決める

設計書のファイル一覧を貼り付けて、観点表の「対象設計書」「参照設計書」に書くパターンを決めます。
ファイル一覧は PowerShell で作れます。

```powershell
Get-ChildItem 【設計書のフォルダ】 -Recurse -File -Include *.xlsx,*.xlsm,*.xls | ForEach-Object { $_.Name } | Set-Clipboard
```

```
下は設計書のファイル名の一覧です。観点表の「対象設計書」に書く、設計書の種類ごとのファイル名パターンを決めてください。

【ルール】
- パターンはファイル名（フォルダ名は含まない）に対するワイルドカードで、* は任意の文字列
- 1 つのパターンが別の種類の設計書に当たらないようにする
- 出力は「設計書の種類 | パターン | 当てはまるファイル数 | 当てはまらない・判別できないファイル」の表

【ファイル一覧】
（ここに貼り付け）
```

ファイル名から種類を判別できない場合（ID だけのファイル名をフォルダで分けているなど）は、ツール側の変更が必要です（[9](#9-ツールの改修依頼を整理する)）。

## 5. AI の指摘と人のレビューを比べる

同じ設計書について、AI の結果（`レビュー結果.xlsx` の「指摘一覧」）と人のレビュー指摘を比べ、観点表の直し方を決めます。**調整の中で一番大事なステップです。** 最初の数本の設計書で必ず行ってください。

```
同じ設計書に対する、AI のレビュー指摘と、人のレビュー指摘を比べてください。

【比べ方】
1. 両方にある指摘、AI だけの指摘、人だけの指摘 に分けて表にする
2. AI だけの指摘は、「正しい指摘（人が見落とした）」と「誤った指摘（設計書を読み違えた・基準が厳しすぎる）」に分ける
3. 人だけの指摘は、「観点表に観点がない」「観点はあるが AI が見落とした」「AI では判定できない内容」に分ける
4. 最後に、観点表の修正案（追加する観点、判定基準を直す観点、削除する観点）を、観点表と同じ列の表で出す

【観点表】
（ここに観点表を貼り付け）

【AI の指摘】
（ここに「指摘一覧」シートの 判定・観点ID・場所・指摘内容・根拠 の列を貼り付け）

【人の指摘】
（ここに人のレビュー指摘を貼り付け）
```

## 6. 判定のぶれを確かめる

同じ依頼文を、新しいチャットで 2 回送って得た回答を比べます。結果が変わる観点は、判定基準があいまいな可能性が高いです。

```
下の 2 つは、同じ依頼に対する AI の回答です。観点ごとに判定（OK／NG／要確認）と指摘箇所を比べてください。

【出力】
- 判定または指摘箇所が食い違った観点の一覧（観点ID、1 回目、2 回目、食い違いの理由の推測）
- 食い違いを減らすための判定基準の書き直し案（観点ID | 現在の判定基準 | 書き直し案）

【観点表】
（ここに観点表の該当する行を貼り付け）

【1 回目の回答】
（貼り付け）

【2 回目の回答】
（貼り付け）
```

## 7. 回答形式を出し直させる

`Invoke-DesignReview.ps1` が「回答から『観点ID | 判定 | ...』の行を読み取れませんでした」と警告したときに、**同じチャットで**送ります。

```
回答を、指定した回答形式どおりに出し直してください。
- 1 行に 1 件、区切りは半角の「|」で「観点ID | 判定 | 場所 | 指摘内容 | 根拠」の 5 項目
- 観点ID は依頼に書かれたとおり（太字などの装飾をしない）
- 判定は OK／NG／要確認 のどれか
- すべての観点について 1 行以上
- 前置き・まとめ・表の見出しは出力しない
```

## 8. レビュー結果を要約する

`レビュー結果.xlsx` の「指摘一覧」を貼り付けて、レビュー会議や報告用に要約させます。

```
下は、設計書のレビュー指摘の一覧です。レビュー会議で共有するための要約を作ってください。

【出力】
1. 全体の傾向（3～5 行）：どの種類の指摘が多いか、どの設計書に集中しているか
2. 重要度「高」の指摘の一覧（設計書 | 場所 | 指摘内容）
3. 複数の設計書で共通して起きている問題と、まとめて直す方法の提案
4. 次の工程に進む前に必ず直すべきもの

【注意】
- 指摘一覧にないことを付け加えない
- 判定が「要確認」のものは、確認が必要な事項として 2. とは分けて挙げる

【指摘一覧】
（ここに貼り付け）
```

## 9. ツールの改修依頼を整理する

ツールの変更が必要なとき（設計書の種類をファイル名で判別できない、赤字で改訂箇所を表している など）に、**社外秘の内容を含まない改修依頼**を Copilot にまとめさせます。できたメモをツールの保守担当（Claude Code）に渡してください。

```
社内の設計書を、外部のツール開発者に見せずに説明するためのメモを作ってください。
下の設計書（または依頼文）を読んで、「書き方の特徴」だけを抽出します。

【抽出すること】
- ファイル名の付け方とフォルダ構成の規則（実際の名前は「ABC-01-0001」のような架空の例に置き換える）
- シートの構成（シート名の種類と役割）と、各シートの表の見出し（列名）
- 1 ファイルあたりのおおよその大きさ（シート数、表の行数）
- 色・取り消し線・図形・画像など、文字以外で意味を表している書き方
- 帳票ヘッダ（各シート上部の共通部分）が何行あるか

【守ること】
- 業務内容、顧客名、システム名、人名、実データは一切含めない
- 列名などの一般的な用語は残してよい

【設計書】
（ここに貼り付け）
```

## 10. 差分から改訂履歴の下書きを作る

`Compare-Excel.ps1` で前の版との差分を CSV にして貼り付け、改訂履歴の下書きを作らせます。
改訂履歴の書き漏れ（直したのに書いていない変更）の確認にも使えます。
書き漏れの確認だけなら、`Compare-Excel.ps1 -CheckHistory` でも Copilot を使わずにできます（書かれていない変更と下書きの文を出力します）。

```powershell
.\Compare-Excel.ps1 .\v1.0\テーブル定義書.xlsx .\v1.1\テーブル定義書.xlsx |
    Select-Object Sheet, Location, Kind, Change, Old, New |
    ConvertTo-Csv -NoTypeInformation | Set-Clipboard
```

```
下は、設計書の前の版と今の版の差分（セル単位）です。改訂履歴の下書きを作ってください。

【出力】
次の列の表で出力してください（改訂履歴シートに貼り付けます）。
改訂箇所 | 改訂内容

【条件】
- 改訂箇所はシート名（テーブル定義書ならテーブル名、画面設計書なら画面名など、シートが表すもの）
- 改訂内容は「何を・どう変えたか」を 1 行で。セル番地や旧の値の羅列ではなく、意味が分かる書き方にする
  （例:「受注テーブルに配送時間帯（DELIVERY_TIME_KBN）の列を追加」「顧客コードの桁数を 8 桁から 10 桁に変更」）
- 同じ目的の変更（列の追加に伴う行の挿入と関連セルの変更など）は 1 行にまとめる
- 書式の調整・誤字の修正のような軽微な変更は、最後に「軽微な修正」として 1 行にまとめる
- 改訂履歴シートそのものの差分は除く
- 差分から意図が読み取れない変更は、改訂内容の先頭に【要確認】と付ける

【改訂履歴に書いた内容】（あれば。書き漏れ・書き過ぎがあれば最後に指摘してください）
（ここに今の版の改訂履歴を貼り付け）

【差分】
（ここに貼り付け）
```
