# 工程別ガイド

どの工程で、どのツールを、どの順に使うかをまとめたページです。各ツールの細かい使い方は [tools/README.md](../tools/README.md) を見てください。
コマンドは `tools` フォルダで実行する例です。PowerShell に慣れていない人は、**ツールの画面**（`tools\Start-ExcelTools.cmd` をダブルクリック、Install-ExcelTools で入れた PC ではスタートメニューの「Excel ツール」）で、各ツールを選んでファイルを入れて実行できます。右クリックの「送る」からも使えます（「送る」の列。`.\Install-SendTo.ps1` を 1 回実行して登録）。

| 工程 | やること | ツール | 「送る」 |
| --- | --- | --- | --- |
| [1. 設計書を作る](#1-設計書を作る) | 一覧から設計書をまとめて作る・表記をそろえる・用語集の下書きを作る・設計書どうしの食い違いを直す・画面の丸数字と古いスクリーンショットを確かめる・画面遷移図と ER 図を作る | New-DesignDocument・Test-ExcelTerms・New-GlossaryDraft・Test-DesignConsistency・Test-ScreenNumbers・Test-Screenshots・Export-TableDdl・Export-DesignDiagram | 表記ゆれ・設計書の整合性チェック |
| [2. 設計レビュー](#2-設計レビュー) | AI に先にレビューさせる・指摘を集計する・AI と人の指摘から観点表を直す | Invoke-DesignReview・Measure-ReviewQuality・Compare-ReviewFindings | － |
| [3. 提出する](#3-提出する) | 版を上げる・改訂履歴の書き漏れを見る・体裁と情報漏れを確かめる・PDF にする・成果物一覧を作る | New-DesignDocument -Bump・Compare-Excel・Test-ExcelDeliverable・Reset-ExcelView・Export-ExcelToPdf・New-DocumentRegister | 提出前チェック・表示を整える・差分・PDF にする |
| [4. 見積もり・進捗](#4-見積もり進捗) | 規模と工数の目安を出す・見積書を検算する・WBS の下書きを作る・遅れと工数の超過を見る・議事録の宿題を集める・週次報告を作る | Measure-DesignSize・Test-ExcelEstimate・New-WbsDraft・Measure-Progress・Measure-Effort・Export-ActionItems・New-WeeklyReport | 規模の見積もり・見積書の検算・議事録の宿題・週次報告 |
| [5. テスト設計](#5-テスト設計) | テスト仕様書の下書きを作る・書き方とケースの不足を確かめる・テストの抜けを見る・テストデータを作る | New-TestSpecDraft・Test-TestSpec・Test-Traceability・New-TestData | テスト仕様書の下書き |
| [6. テスト実施](#6-テスト実施) | 設計書とソースの ID を突き合わせる・消化・バグの収束・密度を見る・エビデンスの抜けと使い回しを見る・障害の横展開の候補を探す | Test-CodeTrace・Measure-TestQuality・Measure-CodeSize・Test-TestEvidence・Find-SimilarDefects | － |
| [7. 改修（仕様変更）](#7-改修仕様変更) | 変わったところと影響を調べる・再テストするケースを選ぶ・追加の見積もり | Compare-Excel・Compare-SharePointVersion・Test-DesignConsistency -Where・Test-ScreenNumbers -Baseline・Select-RegressionTests・Measure-DesignSize -Baseline | 差分・SharePoint の版と比べる |
| [8. 品質会議（工程完了判定）](#8-品質会議工程完了判定) | 品質評価のブックを作る・定性分析と対策の下書きを書く | New-QualityReport・Invoke-QualityAnalysis | 品質評価・品質評価の定性分析 |

どの工程でも、探す・まとめて直すには [Search-Excel](../tools/README.md#search-excelps1)・[Replace-Excel](../tools/README.md#replace-excelps1) を使います（「送る」→「検索」）。

## 1. 設計書を作る

1. 画面一覧などの一覧から、雛形の差し込み欄を埋めた設計書をまとめて作ります（[New-DesignDocument](../tools/README.md#new-designdocumentps1)）
2. 書いている途中で、表記ゆれ（ユーザ／ユーザー など）を見つけて置換リストを作り、Replace-Excel でそろえます（[Test-ExcelTerms](../tools/README.md#test-exceltermsps1)）。用語集がまだ無ければ、設計書から用語集の下書きと表記ゆれの用語集を作り、`-Glossary` に渡します（[New-GlossaryDraft](../tools/README.md#new-glossarydraftps1)）
3. 設計書どうしの参照の食い違い（定義の無いテーブル・メッセージ・コード、画面一覧との過不足、桁数の違い）を直します（[Test-DesignConsistency](../tools/README.md#test-designconsistencyps1)）
4. 画面レイアウトのスクリーンショットに重ねた丸数字（①・No.5 など）が、画面項目定義の No にあるか、同じ番号が重なっていないかを確かめます（[Test-ScreenNumbers](../tools/README.md#test-screennumbersps1)）
5. スクリーンショットが、元のワイヤーフレームより古くなっていないかを確かめます。貼り替えたら `-Record` で記録しておきます（[Test-Screenshots](../tools/README.md#test-screenshotsps1)）
6. テーブル定義書から DDL を作り、DB の列と食い違っていないかを確かめます（[Export-TableDdl](../tools/README.md#export-tableddlps1)）
7. 設計書から画面遷移図と ER 図を作り、遷移先・外部キーの参照先の書き間違いを見つけます。図は設計書を直すたびに作り直せます（[Export-DesignDiagram](../tools/README.md#export-designdiagramps1)）

```powershell
.\New-GlossaryDraft.ps1 D:\設計書 -OutXlsx D:\用語集の下書き.xlsx -OutCsv D:\用語集.csv
.\Test-ExcelTerms.ps1 D:\設計書 -OutCsv D:\置換リスト.csv
.\Test-DesignConsistency.ps1 D:\設計書 -OutXlsx D:\整合性.xlsx
.\Test-ScreenNumbers.ps1 D:\設計書 -OutXlsx D:\画面の番号.xlsx
.\Test-Screenshots.ps1 D:\設計書 -Wireframe D:\ワイヤーフレーム
.\Export-DesignDiagram.ps1 D:\設計書 -OutMarkdown D:\図.md -OutXlsx D:\図.xlsx
```

## 2. 設計レビュー

1. 人がレビューする前に、観点表に沿って Copilot にレビューさせ、明らかな漏れを先に直します。桁数の空欄・メッセージIDの過不足のように数える・突き合わせるだけの観点は、ツールが確かめて同じ指摘一覧に入れます（[Invoke-DesignReview](../tools/README.md#invoke-designreviewps1)）
2. 版を上げた設計書のレビューでは、AI にも前の版から変わった部分だけを渡せます（Invoke-DesignReview の `-Baseline`）。差分の画面（[Compare-Excel](../tools/README.md#compare-excelps1) `-OutHtml`）で変わったところに OK・指摘を付け、指摘を CSV に保存して指摘管理表にできます。人のレビューの指摘を指摘管理表に書き、指摘件数・指摘密度・未完了・期限切れを集計します。レビュー記録があれば、レビュー工数とのゾーン分析もします（[Measure-ReviewQuality](../tools/README.md#measure-reviewqualityps1)）
3. 設計書を直したら、前のレビューの指摘が直ったかを確かめます（Invoke-DesignReview の `-Recheck`）。AI の指摘は AI が、ツールの指摘はツールが確かめ直します
4. AI の指摘と人の指摘を突き合わせ、「観点表への反映案」で観点表を直します。次の設計書から AI のレビューが良くなります（[Compare-ReviewFindings](../tools/README.md#compare-reviewfindingsps1)）

```powershell
.\Invoke-DesignReview.ps1 D:\設計書
.\Measure-ReviewQuality.ps1 D:\レビュー -DesignPath D:\設計書 -ReviewLog D:\レビュー記録.csv -OutXlsx D:\レビュー.xlsx
.\Compare-ReviewFindings.ps1 D:\design-review\レビュー結果.xlsx D:\レビュー\指摘管理表.xlsx -OutXlsx D:\AIと人の比較.xlsx
```

## 3. 提出する

1. 版を上げます（表紙の版数・更新日、改訂履歴の行、ファイル名の版数）。前の版との差分から改訂内容も書けます（[New-DesignDocument -Bump](../tools/README.md#new-designdocumentps1)）。ファイル名の版数を上げると、版を上げる前のファイルが同じフォルダに残ります。設計書を読むツールは版数の大きいファイルだけを読みます（[設計書を読むツールが読まないもの](../tools/README.md#設計書を読むツールが読まないもの)）
2. 前の版と比べ、改訂履歴に書き漏れが無いかを確かめます（[Compare-Excel](../tools/README.md#compare-excelps1)。`-CheckHistory`）
3. 体裁・消し忘れ・情報漏れ・印刷のはみ出し・版数の食い違い・スクリーンショットの縦横比の崩れや拡大しすぎを確かめ、直せるものは `-Fix` で直します（[Test-ExcelDeliverable](../tools/README.md#test-exceldeliverableps1)）。Word の文書（.docx）も、承諾し忘れた変更履歴・コメント・隠し文字の残りを確かめます
4. 開いたときに先頭シートの A1 が表示される状態にそろえ（[Reset-ExcelView](../tools/README.md#reset-excelviewps1)）、必要なら PDF にします（[Export-ExcelToPdf](../tools/README.md#export-exceltopdfps1)。Excel が必要）
5. 提出するフォルダから成果物一覧（文書番号・文書名・版数・更新日・最新の改訂）を作り、古い版が混ざっていないか、版数を直し忘れていないか、予定の成果物がそろっているかを確かめます（[New-DocumentRegister](../tools/README.md#new-documentregisterps1)。`-Planned`）。前回の提出の一覧と比べると、版数を上げずに直した文書と無くなった文書が分かり（`-Previous`）、指摘管理表を渡すと、対応の終わっていない指摘の残る成果物が分かります（`-Findings`）

```powershell
.\Test-ExcelDeliverable.ps1 D:\提出物 -OutXlsx D:\提出前チェック.xlsx
.\Reset-ExcelView.ps1 D:\提出物
.\New-DocumentRegister.ps1 D:\提出物 -Planned D:\成果物の予定.xlsx -Previous D:\成果物一覧_前回.xlsx -Findings D:\レビュー -OutXlsx D:\成果物一覧.xlsx
```

## 4. 見積もり・進捗

- 設計書から画面・テーブル・IF などの規模を数え、工数の目安と FP を出します（[Measure-DesignSize](../tools/README.md#measure-designsizeps1)）
- 見積書の合計の範囲漏れ・手入力の合計などを検算します（[Test-ExcelEstimate](../tools/README.md#test-excelestimateps1)）
- 規模の見積もりの工数を工程に配分し、担当者と予定日を決めた WBS の下書きを作ります。この WBS は、進捗・工数・週次報告のツールがそのまま読めます（[New-WbsDraft](../tools/README.md#new-wbsdraftps1)）
- WBS から遅延タスクと PV／EV を出し、遅れたらスケジュール遅延リカバリ計画に書き込みます（[Measure-Progress](../tools/README.md#measure-progressps1)。`-FillTemplate`）
- 日報・工数実績表の工数をタスク・担当者・週ごとに集計し、WBS の予定工数を超えた・超えそうなタスクを早めに見つけます（[Measure-Effort](../tools/README.md#measure-effortps1)）
- 会議のあとに、議事録から宿題（担当・期限付き）と決定事項を抜き出し、課題管理表に移します（[Export-ActionItems](../tools/README.md#export-actionitemsps1)。「送る」→「議事録の宿題」）
- 毎週、WBS・指摘管理表・障害管理表・課題（QA）管理表から週次報告（今週の完了・遅延・来週の予定、指摘・障害・課題の期限切れ、担当者ごとのやること）を作り、文章をメールやチャットに貼ります（[New-WeeklyReport](../tools/README.md#new-weeklyreportps1)。案件のフォルダに `週次報告の設定.csv` を置き、「送る」→「週次報告」）

```powershell
.\New-WbsDraft.ps1 D:\設計書 -Start 2026-11-02 -Members 山田, 佐藤 -Holidays .\syukujitsu.csv -OutXlsx D:\PJ\WBS.xlsx
.\New-WeeklyReport.ps1 D:\PJ
```

## 5. テスト設計

1. 画面設計書から、必須・桁数・型・コード値・イベントのケースの下書きを作り、画面固有のケースを書き足します（[New-TestSpecDraft](../tools/README.md#new-testspecdraftps1)）
2. テスト仕様書の書き方（期待結果の空欄・「正しく」などのあいまいさ・重複）と、設計書から見たケースの不足を確かめます。不足とは、必須・型・境界値・コード値・メッセージ ID と文言・項目名の揺れです（[Test-TestSpec](../tools/README.md#test-testspecps1)。`-DesignPath`）
3. 要件 → 設計書 → テスト仕様書のつながりと、画面・イベント・メッセージ・IF にテストがあるかを確かめます（[Test-Traceability](../tools/README.md#test-traceabilityps1)）
4. テーブル定義書から、そのまま登録できるテストデータ（CSV と INSERT 文。桁数の最大・最小・NULL の行も）を作ります（[New-TestData](../tools/README.md#new-testdataps1)）

```powershell
.\New-TestSpecDraft.ps1 D:\設計書 -OutXlsx D:\テスト仕様書\UT_下書き.xlsx
.\Test-TestSpec.ps1 D:\テスト仕様書 -DesignPath D:\設計書 -OutXlsx D:\テスト仕様書のチェック.xlsx
.\Test-Traceability.ps1 -DesignPath D:\設計書 -TestPath D:\テスト仕様書 -Requirement D:\要件一覧.xlsx -OutXlsx D:\網羅.xlsx
.\New-TestData.ps1 D:\設計書 -OutDir D:\テストデータ -Database PostgreSQL
```

## 6. テスト実施

- テストの前（製造の終わり）に、設計書のメッセージ・画面・テーブルの ID をソースで使っているか、ソースで使っている ID が設計書にあるか（書き間違い・設計書の直し忘れ）を突き合わせます（[Test-CodeTrace](../tools/README.md#test-codetraceps1)）
- テストの消化、バグの収束（信頼度成長曲線）、機能ごとのテスト密度・バグ密度を見ます。再テスト漏れなど、テスト仕様書と障害管理表の食い違いも見つけます（[Measure-TestQuality](../tools/README.md#measure-testqualityps1)）
- 密度の分母に KLOC を使うときは、ソースのステップ数を数えます（[Measure-CodeSize](../tools/README.md#measure-codesizeps1)。`-OutCsv` を Measure-TestQuality の `-SizeCsv` に渡す）
- テスト仕様書を提出する前に、実施したケースのエビデンス（画面のハードコピーなど）がそろっているか、同じ画像を使い回していないか、結果を書き忘れたケースが無いかを確かめます（[Test-TestEvidence](../tools/README.md#test-testevidenceps1)）
- 障害を直したら、同じ作り（型・入力チェック・処理など）の箇所を設計書から集めて横展開の候補にし、Copilot に絞り込ませてから確かめます（[Find-SimilarDefects](../tools/README.md#find-similardefectsps1)。`-OutPrompt` と `-Answer`）

```powershell
.\Test-CodeTrace.ps1 D:\設計書 D:\src -OutXlsx D:\設計とソースの突き合わせ.xlsx
.\Test-TestEvidence.ps1 D:\テスト仕様書 -EvidencePath D:\エビデンス -OutXlsx D:\エビデンスのチェック.xlsx
.\Find-SimilarDefects.ps1 D:\テスト\障害管理表.xlsx D:\設計書 -Id B012 -OutXlsx D:\横展開.xlsx -OutPrompt D:\横展開の依頼.txt
```

## 7. 改修（仕様変更）

1. 旧版と新版の設計書の差分を取ります。`-OutHtml` で、変わったセルに色を付けたシートをブラウザーで見られます（[Compare-Excel](../tools/README.md#compare-excelps1)。「送る」→「差分」もこの画面を開きます）。Word の設計書（.docx）も段落と表の行で比べます。v1.0・v1.1・v1.2 のように版がいくつもあるときは、`-Versions` で版の順に続けて比べます（「送る」で 3 つ以上選んだときも）。SharePoint に置いた設計書は、バージョン履歴の番号を指定して前の版と比べられます（[Compare-SharePointVersion](../tools/README.md#compare-sharepointversionps1)。「送る」→「SharePoint の版と比べる」）
2. 変えたテーブル・メッセージ・コードを、どの設計書が使っているかを調べます（[Test-DesignConsistency](../tools/README.md#test-designconsistencyps1)。`-Where`）
3. 画面項目定義に項目を足して No がずれたときは、スクリーンショットに重ねた丸数字が古いままになっていないかを、旧版と比べて確かめます（[Test-ScreenNumbers](../tools/README.md#test-screennumbersps1)。`-Baseline` に旧版）
4. 差分から、再テストするテストケースを選びます。テストが見つからない変更も分かります（[Select-RegressionTests](../tools/README.md#select-regressiontestsps1)）
5. 変更の規模から、追加の見積もりの根拠を作ります（[Measure-DesignSize](../tools/README.md#measure-designsizeps1)。`-Baseline` に旧版）

```powershell
.\Compare-Excel.ps1 D:\設計書_v1.0 D:\設計書_v1.1 -OutHtml D:\差分.html
.\Compare-Excel.ps1 -Versions D:\設計書\版 -OutHtml D:\版の差分.html
.\Test-ScreenNumbers.ps1 D:\設計書_v1.1 -Baseline D:\設計書_v1.0 -OutXlsx D:\画面の番号.xlsx
.\Select-RegressionTests.ps1 -Old D:\設計書_v1.0 -New D:\設計書_v1.1 -TestPath D:\テスト仕様書 -OutXlsx D:\再テスト.xlsx
.\Measure-DesignSize.ps1 D:\設計書_v1.1 -Baseline D:\設計書_v1.0 -OutXlsx D:\変更の規模.xlsx
```

## 8. 品質会議（工程完了判定）

1. 案件のフォルダに「品質評価の設定.csv」（ひな形は `tools\quality-report\品質評価の設定_ひな形.csv`）を置き、品質評価のブックを作ります。レビュー・テスト・工程別の摘出・網羅・整合性の各ツールをまとめて実行し、指標・実績・判定（○△×）・要対応を 1 冊にします（[New-QualityReport](../tools/README.md#new-qualityreportps1)）
2. × と △ の指標の定性分析（原因）と対策の下書きを Copilot に書かせます。前回の対策が効いたかも書いてもらえます。下書きは会議の前に必ず確かめて直します（[Invoke-QualityAnalysis](../tools/README.md#invoke-qualityanalysisps1)）

```powershell
.\New-QualityReport.ps1 -Config D:\案件\受注システム
.\Invoke-QualityAnalysis.ps1 D:\案件\受注システム\品質報告
```

「送る」なら、案件のフォルダを「Excel 品質評価」に、できた品質評価のブックを「Excel 品質評価の定性分析」に送ります。

## 9. プロジェクトの終わり

品質評価の実績の CSV（`-HistoryCsv`。設定ファイルの「実績」）を集め、次の案件の指摘密度・テスト密度・バグ密度の基準値を作ります（[New-QualityLimits](../tools/README.md#new-qualitylimitsps1)）。

```powershell
.\New-QualityLimits.ps1 D:\品質実績 -OutCsv D:\基準値.csv
```
